Ein Rechner arbeitet in Schichten: Hardware, Betriebssystem, Anwendungen. Jede Ebene nutzt die Dienste der darunterliegenden.

Arbeite mit einem kleinen Beispiel, formuliere den Ablauf eindeutig und prüfe ihn mit Gegenfällen.

Internetprotokolle

IP adressiert und transportiert Pakete zwischen Netzen. TCP stellt Anwendungen einen geordneten, zuverlässigen Bytestrom bereit, kann bei anhaltenden Störungen aber mit einem Fehler enden. HTTP beschreibt die Nachrichten der Webanwendung. HTTP/1.1 und HTTP/2 werden häufig über TCP genutzt; HTTP/3 verwendet QUIC.

HTTP regelt, wie Browser und Webserver Seiten austauschen, HTTPS verschlüsselt diese Verbindung zusätzlich. Die Protokolle bauen wie Schichten aufeinander auf.

Client

Der Client stellt eine Anfrage, der Server beantwortet sie. Ein Browser ist ein Client, der Rechner mit der Website ein Server.

Beim Aufruf einer Webseite schickt der Browser eine Anfrage, der Server liefert die Seite zurück. Viele Clients können gleichzeitig denselben Server nutzen.

Anwendung, Transfer

Zum Abschluss überträgst du die drei Kernbereiche auf eine neue Situation. Eine gute Lösung nennt Ausgangslage, Vorgehen, Ergebnis und Kontrolle.

Entwirf eine kleine digitale Lösung und begründe Datenmodell, Ablauf, Tests und Schutzmassnahmen. Die Begründung muss zeigen, warum das Vorgehen zur Frage passt.

Genauer betrachtet

DNS ordnet Namen den für einen Dienst benötigten Adressinformationen zu. IP beschreibt die Weiterleitung von Paketen. Transportprotokolle ermöglichen die Kommunikation zwischen Anwendungen, und HTTP beschreibt Webnachrichten. Die Schichten sind ein Denkmodell; sie ersetzen keine Beobachtung des konkreten Fehlers.

Ein erfolgreicher Schritt beweist nicht automatisch den nächsten. Eine DNS-Antwort bedeutet nicht, dass der Webdienst erreichbar ist. Eine hergestellte Verbindung beweist noch keine korrekte Antwort der Anwendung. Ein HTTP-Fehler kann sogar zeigen, dass die vorherigen Schichten gearbeitet haben.

Diagnose beginnt mit einer sicheren, begrenzten Fragestellung. In diesem Unterrichtsfall werden nur fiktive Protokolle gelesen. Es werden keine fremden Systeme gescannt und keine Sicherheitswarnungen deaktiviert.

Durchgerechnete Beispiele

Rechnersysteme und Netzwerke

Aufgabe: Fiktive Ereignisse: A, Namensauflösung für kurs.example scheitert. B, Namensauflösung gelingt, Verbindung zum Dienst erreicht ihr Zeitlimit. C, gesicherte Verbindung gelingt, der Server antwortet HTTP 404. D, Server antwortet HTTP 200, die Anwendung zeigt eine leere Liste.

  1. Fall A betrifft bereits die Namensauflösung. Eine Antwort über einen Tippfehler oder die DNS-Konfiguration wäre eine Prüfhypothese, noch kein bewiesener Grund.
  2. Fall B liegt später: Die Adresse ist bekannt, aber der Dienst antwortet innerhalb der beobachteten Zeit nicht. Ursache können Server, Netz oder Filter sein. Das Protokoll bestimmt sie noch nicht eindeutig.
  3. Fall C liefert eine Webantwort. Der angefragte Inhalt wurde nicht gefunden. Daraus folgt nicht, dass der gesamte Internetzugang ausgefallen ist.
  4. Fall D erfordert eine Anwendungskontrolle. HTTP 200 belegt die erfolgreiche HTTP-Antwort, aber nicht, dass die gesuchten Datensätze fachlich vorhanden oder richtig gefiltert sind.

Ergebnis: Die vier Fälle erfordern vier verschiedene nächste Prüfschritte. Ein Statuscode oder ein Netzsymbol ersetzt keine Ende-zu-Ende-Kontrolle des gewünschten Inhalts. Kontrolle: Ordne jeden Fall nach dem zuletzt belegten erfolgreichen Schritt. Alle weitergehenden Ursachen bleiben als Hypothesen kenntlich.

Grenzen: Die Protokolle sind fiktiv. Ein echtes Diagnoseverfahren benötigt Zugriffserlaubnis, sichere Werkzeuge und den konkreten Netzwerkaufbau.

Verständnis prüfen

Offene Fragen mit Musterantwort aus der KI-Prüfung. Es gibt keine automatische Bewertung.

Beweist ein WLAN-Symbol die Erreichbarkeit der Webseite?

Nein. Es zeigt höchstens einen lokalen Verbindungszustand. Namensauflösung, Server und Anwendung können trotzdem scheitern.

Warum darf eine Zertifikatswarnung nicht einfach weggeklickt werden?

Sie betrifft die Sicherheitsprüfung der Gegenstelle. Ihr Umgehen ist keine fachgerechte Lösung eines Verbindungsproblems.

Was muss bei HTTP 200 mit leerer Liste noch geprüft werden?

Die tatsächliche Antwort, Filter, Berechtigungen und die fachliche Erwartung. Transporterfolg ist nicht gleich Inhaltsrichtigkeit.

Typischer Fehler

Eine plausible Ausgabe beweist noch nicht, dass ein Algorithmus für alle Fälle korrekt ist.
